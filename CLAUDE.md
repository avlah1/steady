# CLAUDE.md

## Project

Hackathon project (LA Hacks, 24 hours): a fall-detection system for elderly people who live alone.
A camera watches the person; when a fall is detected, a voice assistant asks "Are you okay?",
an LLM interprets the spoken reply, and if they need help or don't respond, caregivers are alerted.

**Current scope: fall detection only.** Behavior learning, vitals, and daily summaries are future work. Do not build them unless asked.

## Architecture

All Python runs on one team laptop. The laptop and both ESP32 boards share one Wi-Fi network (team hotspot).

- **ESP32-CAM + pan servo**: serves an MJPEG video stream; exposes `GET /pan?angle=N` to rotate the camera.
- **Vision worker** (Python, separate process): pulls frames, runs MediaPipe Pose, tracks the person (sends pan commands), detects falls with rule-based logic on pose landmarks. Sends **events only** (never video) to the backend.
- **FastAPI backend** (this repo's main component): receives detections, runs the incident state machine, talks to the S3-Box, notifies caregivers, stores data.
- **ESP32-S3-BOX-3**: voice device. Connected to the backend over a WebSocket; speaks prompts, records replies and sends audio back.
- **React caregiver dashboard**: reads incidents from the backend.
- **Speech-to-text**: local Whisper (faster-whisper, `base.en` by default) on the laptop. No cloud call, so it works on a weak hotspot.
- **Cloud services**: LLM API (Claude Haiku), Supabase (database), caregiver messaging.

## Design principles

- **The AI never controls escalation.** The LLM only classifies replies into a fixed label. A deterministic state machine decides every transition.
- **Fail safe.** Any timeout or API failure (speech-to-text, LLM) is treated as `unclear`, never as `ok`. Prefer false alarms over missed falls.
- **Endpoints and timers never change state directly.** They all call a single `handle(incident, trigger, data)` function.

## Backend API (v1)

### `POST /api/v1/detections` (vision worker → backend)

```json
{
  "event_id": "uuid generated by the worker",
  "type": "fall_suspected",
  "confidence": 0.87,
  "detected_at": "2026-10-17T14:31:05Z",
  "camera_id": "living_room",
  "details": { "hip_drop": 0.42, "torso_angle_deg": 12, "seconds_down": 5.2 }
}
```

Response: `202 {"incident_id": "...", "created": true|false}`. Respond immediately; never block on the incident flow.

Rules, in order:
1. **Duplicate `event_id`** (worker retry): return the original response, do nothing else (idempotent).
2. **Active incident exists for this `camera_id`** (state `OPEN`, `ASKING`, or `ESCALATED`): attach the event to it, return `created: false`. Do not restart the prompt sequence.
3. **Otherwise**: create an incident and call `handle(incident, "new_fall")`.

Requires header `X-API-Key` (shared secret from `.env`).

### Other endpoints (to be detailed)

- `POST /api/v1/box/reply/audio`: Box sends recorded WAV → speech-to-text → LLM label → `handle(incident, label)`
- `POST /api/v1/box/reply`: same but with text (testing; skips speech-to-text)
- `POST /api/v1/incidents/{id}/ack`: caregiver acknowledges → `handle(incident, "ack")`
- `GET /api/v1/incidents`, `GET /api/v1/incidents/{id}`: for the dashboard
- `WS /ws/box`: Box stays connected; backend pushes text for it to speak

## Incident state machine

States: `OPEN`, `ASKING` (with `attempt` 1–3), `RESOLVED_OK` (terminal), `ESCALATED`, `ACKNOWLEDGED` (terminal).

| Trigger | From | To | Side effect |
|---|---|---|---|
| `new_fall` | — | `OPEN` → `ASKING` (attempt 1) | Box asks "Are you okay?", start reply timer |
| reply `ok` | `ASKING` | `RESOLVED_OK` | Box confirms |
| reply `needs_help` | `ASKING` | `ESCALATED` | Alert first caregiver, start ack timer |
| reply `unclear` or reply timeout | `ASKING` | `ASKING` (attempt + 1) | Ask again, restart reply timer |
| attempt 3 fails | `ASKING` | `ESCALATED` | Alert first caregiver, start ack timer |
| ack timeout | `ESCALATED` | `ESCALATED` | Alert next caregiver, restart ack timer |
| `ack` | `ESCALATED` | `ACKNOWLEDGED` | Box: "Help is coming" |

- **Emergency services** is a contact with `kind: emergency`, placed in the order by the user. Alert is simulated (log line). It's never waited on (next contact alerted immediately) and alerted at most once per incident. The incident still needs a person's `ack`.
- Every transition is appended to the incident's timeline (timestamp, from, to, trigger).
- Timers are `asyncio` tasks per incident, cancelled on every transition.
- **Stale timers:** when a timer fires, `handle` must verify the incident is still in the state/attempt the timer was created for; otherwise ignore it.
- Timer durations come from config. Demo values: ~10 s per ask, ~30 s per ack.

## LLM reply classification

`classify_reply(question, transcript) -> "ok" | "needs_help" | "unclear"`

- Request JSON output with only those three labels.
- Prompt leans cautious: any sign of pain, confusion, or distress → `needs_help`.
- Timeout of a few seconds; on failure return `unclear`.
- API keys live only in the backend `.env`.

## Data (Supabase)

Three tables for now: `contacts` (who to alert, in order), `events` (raw detections), `incidents` (state, attempt, timeline). Start with in-memory storage or SQLite behind a small repository layer, then swap to Supabase.

## Development

- Stack: Python 3.11+, FastAPI, Pydantic v2, pytest.
- Until hardware is ready, **fake the Box and caregiver notifications as log lines** (e.g. `BOX SAYS: Are you okay?`, `ALERT -> contact 1`). Keep them behind interfaces so real implementations drop in later.
- Test the flow by posting fake detections with `curl` or a small script.
- Write tests for the state machine transitions, including the stale-timer race and duplicate `event_id`.
- Small, focused commits. Explain non-obvious choices; the team is learning as we go.
- Keep `docs/api.md` and `docs/state-machine.md` current: update them in the same commit as any endpoint or state machine change. Plain language, brief.
- Secrets in `.env` (gitignored): API keys, Supabase URL/key, `X-API-Key` secret.
